# Story 2.3: Drag-Reorder Outline

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Instructor,
I want to reorder Modules and Lessons by dragging them in the outline,
so that I can restructure my course without opening each item individually.

## Acceptance Criteria

1. **Given** I am viewing the outline editor, **when** I drag a Lesson to a new position within its Module, or a Module to a new position in the course, **then** the new order is reflected immediately and autosaved, without opening the dragged item.
2. **Given** I am using Arabic (RTL), **when** I drag-reorder, **then** drag direction and drop-indicator placement mirror correctly for RTL.
3. **Given** I prefer or need keyboard-only interaction, **when** I focus a Module or Lesson row, **then** an explicit "move up / move down" control (or arrow-key reordering) is available as a full keyboard equivalent to dragging, with a visible/audible confirmation of the new position.

## Tasks / Subtasks

- [x] Task 1: Service layer — sibling-list reorder writes (AC: #1)
  - [x] Extend `lib/modules/course-authoring/service.ts` (siblings of `addModule` / `updateModuleTitle` / `getCourseOutline` — plain functions, direct Drizzle, return value/`null`, **no `{ok,…}` wrapping**; that is the action-layer convention). Authorization stays out of the service — it lives in `actions.ts`.
  - [x] `reorderModules({ courseId, orderedModuleIds }): Promise<{ ok: true } | { ok: false; reason: "mismatch" }>` — rewrites `module.position` so the given `courseId`'s **non-removed** modules match `orderedModuleIds` order (index 0 → `position` 0, contiguous). Before writing, load the current non-removed module id set for that course and assert `orderedModuleIds` is a permutation of it (same length, same members, no dupes). On mismatch return `{ ok: false, reason: "mismatch" }` and write nothing — the client's optimistic order and the DB diverged (a stale tab, a concurrent add, or a crafted payload); the action maps this to `{ code: "stale_outline" }` and the client re-syncs from a fresh `getCourseOutline`.
  - [x] `reorderLessons({ moduleId, orderedLessonIds }): Promise<{ ok: true } | { ok: false; reason: "mismatch" }>` — identical contract, scoped to one Module's non-removed lessons. **Lessons only reorder *within* their Module** (AC #1 wording: "within its Module") — there is no cross-module move in this story; do not accept a `moduleId` change here.
  - [x] Both are pure position rewrites: `title`, `lessonType`, `required`, `removedAt` are never touched. `updatedAt` advances on the rows whose `position` actually changed (Drizzle `$onUpdate` handles it on any row included in the `SET`).
- [x] Task 2: Collision-safe position rewrite — one statement, not a loop (AC: #1)
  - [x] `module` and `lesson` each carry a **partial unique index** on `(parent_id, position) WHERE removed_at IS NULL` (`module_course_position_uq` / `lesson_module_position_uq`, added by Story 2.2's migration `0008`). A naive "UPDATE each row to its new position" loop **will** hit `23505` mid-sequence (e.g. swapping positions 0↔1: setting row A to 1 collides with row B still at 1). Do **not** loop per row.
  - [x] Rewrite all affected siblings in **a single `UPDATE` statement** using a `CASE`/`VALUES` mapping of `id → new position`. Postgres evaluates a single multi-row `UPDATE` and checks the unique index **once, after the statement completes** — so a full permutation applies with no transient duplicate. Drizzle: build the `SET position = ...` with `sql`. A `CASE` form is fine for small N:
    ```ts
    // pseudo — inside reorderLessons
    await db.update(lesson)
      .set({
        position: sql`CASE ${lesson.id} ${sql.join(
          orderedLessonIds.map((id, i) => sql`WHEN ${id} THEN ${i}::int`),
          sql` `,
        )} ELSE ${lesson.position} END`,
      })
      .where(and(inArray(lesson.id, orderedLessonIds), isNull(lesson.removedAt)));
    ```
  - [x] `[FALLBACK]` if the single-statement `CASE` proves awkward in Drizzle, the alternative is a `db.transaction`: first `UPDATE … SET position = position + <bigOffset>` (or negative) for the whole sibling set to vacate the [0..n) range, then a second `UPDATE` (or the `CASE`) to final positions. Correct but two statements; prefer the one-statement form.
  - [x] No new migration. `position` (integer, 0-based, contiguous, appended-on-add) and the two partial-unique indexes already exist from Story 2.2 — this story only adds *write* paths that rewrite them. `db:generate` should produce **nothing**; if it does, something drifted — stop and investigate.

## Dev Notes

- **This story adds only *write paths* — no schema change.** `position` (0-based, contiguous `integer`, appended on add) and the two partial-unique indexes `module_course_position_uq` / `lesson_module_position_uq` on `(parent_id, position) WHERE removed_at IS NULL` already exist from Story 2.2 (migrations `0007` + `0008`).   [Source: _bmad-output/implementation-artifacts/2-2-outline-first-module-lesson-structuring.md#Tasks (Task 2); lib/modules/course-authoring/schema.ts]
- **The unique index makes a per-row UPDATE loop fail — rewrite the whole sibling list in one statement.** Story 2.2 added `(parent_id, position)` partial-unique indexes deliberately, to make the append race fail loudly instead of silently duplicating. The cost: any reorder that permutes existing positions cannot be done as sequential single-row UPDATEs (a transient duplicate trips `23505`). Postgres checks a unique index **once at statement end** for a single multi-row `UPDATE`, so one `UPDATE … SET position = CASE id … END WHERE id IN (…)` applies a full permutation cleanly. Fallback is a two-statement transaction (vacate the range via an offset, then set finals). This is the single most important implementation detail in the story — a naive loop will appear to work on a no-op reorder and fail the moment two rows actually swap.
  [Source: lib/modules/course-authoring/schema.ts#module_course_position_uq, #lesson_module_position_uq; web research 2026 — Postgres unique-constraint checking on multi-row UPDATE]
