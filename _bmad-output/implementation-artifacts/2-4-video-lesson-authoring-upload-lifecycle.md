# Story 2.4: Video Lesson Authoring & Upload Lifecycle

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Instructor,
I want to upload a video as a Lesson's content and always see its processing status,
so that I never wonder whether an upload silently failed.

## Acceptance Criteria

1. **Given** I open a Lesson and choose the Video Lesson Type, **when** I upload a video file, **then** the Lesson's media record shows status `queued`, then `processing`, then `ready` (driven by Cloudflare Stream webhooks) — always one of the four canonical states, never silent.
2. **Given** my video upload exceeds the per-Lesson or per-Instructor cap, **when** I attempt the upload, **then** it is rejected at upload time with a clear message — never silently truncated or accepted then billed.
3. **Given** a video upload's processing fails, **when** I view the Lesson, **then** I see a clear failed state — an icon and text label together, never color alone — with an inline Retry action that re-attempts without requiring me to re-select the file.
4. **Given** I am editing this Lesson's video content, **when** I make a change (e.g. replace the video, edit a caption note), **then** it autosaves on pause as its own content-body field group, independent from the Lesson's outline metadata (title/order).
5. **Given** I set this Lesson's content to Video, **when** I check the Lesson's type, **then** it has exactly one Lesson Type — Video — at a time.

- **Cloudflare Stream — verified API shape (web research, Sept 2026).**
  - **Direct creator upload:** `POST https://api.cloudflare.com/client/v4/accounts/{account_id}/stream/direct_upload`, `Authorization: Bearer <token>`, body `{ maxDurationSeconds (required), creator, meta, requireSignedURLs, expiry }`. Response `{ result: { uploadURL, uid } }`. The **basic** `uploadURL` accepts a single `POST` of the file and is **limited to 200 MB**; larger files need the **tus** protocol (`POST …/stream?direct_user=true`, size in the `Upload-Length` header, `maxDurationSeconds` base64 in `Upload-Metadata`). `maxDurationSeconds` reserves storage against your account from creation until the upload lands or the link expires. Set `expiry` ~30 min out.
  - **Webhook:** subscribe once via `PUT …/accounts/{acct}/stream/webhook` `{ notificationUrl }` — the response carries the signing `secret`. Notification body: `{ uid, readyToStream (bool — true once ≥1 quality level is encoded), status: { state, pctComplete, errorReasonCode, errorReasonText }, duration, meta, thumbnail }`. `status.state` is `"inprogress"` | `"ready"` | `"error"` (also `"pendingupload"` / `"downloading"` / `"queued"` for link-uploads — treat anything that isn't `error` and isn't `readyToStream:true` as our `processing`). Signature header: `Webhook-Signature: time=<unix>,sig1=<hex>`; verify `sig1 == HMAC_SHA256(secret, "<time>.<rawBody>")`, constant-time, and reject a `time` skewed more than ~5 min (replay guard). **Read the raw request body** for this — do not `JSON.parse` before verifying.
  - `readyToStream: true` is the signal to flip to `ready` (a known Cloudflare quirk: it can fire before `pctComplete` hits 100 — that's fine for authoring; the learner-facing player quirk is Story 4.3's problem). `[Source: web research — developers.cloudflare.com/stream/uploading-videos/direct-creator-uploads/, /stream/manage-video-library/using-webhooks/, Sept 2026]`

Noted for `code-review`. - **Not done (conscious scope calls / per story):** no video player (Stories 2.9 / 4.3); no tus / resumable upload (fallback above); no monthly-window per-Instructor cap (total-stored cap only — the PRD's "per month" has no reset infra, as the story notes); no stale-`queued` sweep (a media row whose bytes were never uploaded sits at `queued` — acceptable v1, noted).
