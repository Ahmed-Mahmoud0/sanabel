# Story 2.6: PDF Lesson Authoring & Upload Lifecycle

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Instructor,
I want to upload a PDF as a Lesson's content and see its processing status,
so that document-based material is treated with the same reliability as video.

## Acceptance Criteria

1. **Given** I open a Lesson and choose the PDF Lesson Type, **when** I upload a PDF file, **then** it is validated server-side for file type and size, and status is set synchronously to `ready` on success or `failed` on validation failure — never left ambiguous.
2. **Given** my PDF upload exceeds the per-Lesson or per-Instructor cap, or is not a valid PDF, **when** I attempt the upload, **then** it is rejected at upload time with a clear message; no executable or unexpected file type is ever accepted.
3. **Given** a PDF upload fails validation, **when** I view the Lesson, **then** I see a clear failed state — an icon and text label together, never color alone — with an inline Retry action.
4. **Given** I am editing this Lesson's PDF content, **when** I replace the file, **then** it autosaves as its own content-body field group, independent from outline metadata.

- [x] Task 6: PDF **finalize** Route Handler — the synchronous validator, the only writer of `ready` / `failed` for PDF (AC: #1, #2, #3)
  - [x] New `app/api/instructor/pdf-uploads/complete/route.ts` — `POST { lessonId }`, `runtime = "nodejs"`. **Why this exists:** Vercel Functions reject any request body over **4.5 MB** (`413 FUNCTION_PAYLOAD_TOO_LARGE`, platform limit, not configurable), so the PDF bytes cannot be POSTed through a Sanabel route — real lecture PDFs routinely exceed that. The bytes go browser → R2 via the presigned URL; this endpoint is where Sanabel then validates **server-side, synchronously**, which is exactly AD-5's "PDF status is set synchronously after server-side type/size validation". It is a *completion* step, not a second initiation point — caps are still enforced only in the initiation handler (Task 5) and merely **re-verified here against the real object**, because the declared size was client-reported.
  - [x] Same auth/ownership guards as Task 5, then load `data.media`; if there is no live `pdf` row → `404 not_found`; if `media.status !== "queued"` → return `200` with the current state (idempotent; covers a double submit and an already-finalized row). Then, in order:
    1. `headObject(key)` → `null` ⇒ outcome `failed` / `PDF_ERROR_MISSING` (the PUT never landed).
    2. `size > PDF_MAX_BYTES_PER_LESSON` ⇒ `failed` / `PDF_ERROR_TOO_LARGE`, **and** `deleteObject(key)` (the signed length should make this unreachable; this is defense-in-depth against a signing gap — see the Task 3 `[DECISION]`). Also fail (`too_large`) if the real size exceeds the declared `media.sizeBytes` — the object is not what the cap check approved.
    3. `looksLikePdf(await getObjectHead(key, PDF_MIME_SNIFF_BYTES))` false ⇒ `failed` / `PDF_ERROR_NOT_A_PDF` **and** `deleteObject(key)` — never leave a rejected (potentially executable/other) file in the bucket.
    4. Otherwise `ready` with the verified `size`.
    5. Persist via `finalizePdfMedia`; respond `200 { ok: true, data: { status, errorReason } }` (a validation *failure* is a successful finalize that yields `failed` — the client renders the failed state from this response; the route does not use HTTP errors for it). A `null` from `finalizePdfMedia` (lost a race) → re-read the row and return its state.
  - [x] **No `revalidatePath`** (same reasoning as every 2.4/2.5 write). R2/`HEAD` failures (network, 5xx) → `502 provider_error` **without** changing the row — the row stays `queued` and the client's Retry re-runs finalize/upload; don't mark a transient provider error as a validation failure.

- **This story implements AD-5's PDF half, and the architecture already fixed the shape — follow it literally, with one deliberate mechanical adaptation.** AD-5: *one canonical status enum `queued | processing | ready | failed` on the Lesson's media record; **PDF status is set synchronously after server-side type/size validation**; FR-11 caps enforced server-side, once, at that media kind's one upload-initiation Route Handler (one for video, one for PDF — not one shared handler for both, never duplicated per UI surface).* So: `lesson_media.status` is the enum (all four values exist; a PDF row in practice only ever holds `queued`, `ready`, `failed` — `processing` is video-only because there is no async stage); `app/api/instructor/pdf-uploads/route.ts` is the **only** place PDF caps are enforced and the only writer of `queued`; the finalize handler is the **only** writer of `ready`/`failed` for PDF; the client never sets status. The adaptation: AD-5 and SOLUTION-DESIGN §8 imagine a single "PDF upload" Route Handler, which implicitly assumes the bytes pass through it. That cannot work on the chosen host — see next bullet.
  [Source: ARCHITECTURE-SPINE.md#AD-5, #AD-1; SOLUTION-DESIGN.md#8-Source-Tree ("api/ — … PDF upload")]
- **`[DECISION]` Upload mechanics: browser → R2 direct via a presigned `PUT`, then a server-side finalize that validates — recommended and adopted.** Options weighed: (1) **Stream the PDF through a Sanabel Route Handler** (multipart `POST`, validate, then `PutObject`) — simplest, truly "validate before it is stored", but **Vercel Functions cap the request body at 4.5 MB** (`413 FUNCTION_PAYLOAD_TOO_LARGE`; confirmed against Vercel's docs, Oct 2026; it is a platform limit that cannot be raised), and the production host is Vercel (AD-12). A PDF-lesson feature that silently dies on a 6 MB slide deck is not credible; it would also pay function-memory/time for every byte. (2) **Presigned PUT + finalize (chosen)** — bytes never touch Sanabel (zero function egress, consistent with how video already works); the 4.5 MB wall disappears; validation is still server-side and synchronous in the finalize request (HEAD for the real size, a 1 KB ranged GET for the magic bytes), deleting a rejected object immediately. Trade-off, stated honestly: the object exists in the bucket for a moment before it is validated (it is private and un-served, so nothing can read it; a rejected one is deleted in the same request, and an abandoned one is an orphan — see Deferred). (3) Direct-to-R2 with an R2 event notification → queue → validator — async, would need `processing`, adds infrastructure; rejected as exactly the complexity AD-5's "synchronous" wording rules out. If Ahmed would rather keep PDFs ≤ 4 MB and stream through the route, the Route Handler contract (Task 5 caps, Task 6 validation) is unchanged and only the byte path differs — but that cap would have to be stated in the UI.
