- (decision) AD-1 Paradigm: modular monolith -- one Next.js full-stack app is the system of record over one Postgres DB. Binds: every epic/module. Prevents: premature service decomposition a solo builder cannot operate; independent epics inventing their own API/DB-access patterns. Rule: Server Actions/Route Handlers are the only mutation boundary; external capabilities that cannot live in-process (video transcode/delivery, object storage, sandboxed SQL execution as an isolated process, transactional email) are the only carve-outs, each behind a narrow contract.
- (decision) AD-2 Module ownership map: Accounts (User/Session/Role) | Course Authoring (Course/Module/Lesson content+structure) | Learning Experience (Enrollment/Progress/completion) | Certificates (Certificate) | Discussion (Comment) | Ratings (Rating). Binds: which module's service layer owns writes to which tables. Prevents: two epics both writing Progress rows, or Discovery reimplementing enrollment-gating logic independently of Learning Experience.
- (decision) AD-3 Cross-module access rule: a module may only mutate its own tables directly; it reads/writes another module's data exclusively through that module's exported service functions, never raw Drizzle queries against another module's schema. Binds: all module boundaries. Prevents: silent divergence in business rules (e.g. two different definitions of 'is this Learner enrolled') because a shortcut query bypassed the owning module's logic.
- (decision) AD-4 Autosave/concurrency contract (FR-12): course-builder edits autosave via debounced Server Action calls, one call per outline/content field-group; each Lesson/Module row carries an updatedAt-based optimistic version, last-write-wins per field-group. Binds: Course Authoring's outline editor and lesson editors. Prevents: two independently-built editor surfaces (outline vs lesson-content) choosing incompatible save granularity or conflict handling, risking silent data loss.
- (decision) AD-5 Upload lifecycle contract (FR-10, FR-11): one canonical status enum (queued|processing|ready|failed) stored on the Lesson's media record, driven by Cloudflare Stream webhooks (video) and a synchronous validation step (PDF); FR-11 caps enforced server-side at the single upload-initiation Route Handler, never client-side or per-surface. Binds: course-builder upload UI and learner-facing player/viewer. Prevents: the two surfaces (author-side status chip, learner-side playback) disagreeing on what 'ready' means, and cap enforcement being reimplemented (or skipped) per upload entry point.
- (decision) AD-6 Role/authorization contract: Learner/Instructor/Admin are additive flags on one Account (FR-3), not separate entities; Better Auth session carries role claims; every module calls one shared requireRole()/can() helper rather than ad hoc checks. Binds: every Instructor-only or Admin-only surface across all epics. Prevents: FR-3's 'Learner never sees Instructor-only surfaces' being satisfied in one module's UI but missed in another's, or in a route handler that skips the UI-layer check entirely.
- (decision) AD-7 Completion/certificate-eligibility contract: one canonical isLessonComplete()/isCourseComplete() computation, owned by Learning Experience, is the sole input to Progress display, Resume-where-left-off, and Certificate issuance (FR-20/21/25/26). Every Lesson/Quiz/Exercise carries a required:boolean (default true) so completion math has a stable input regardless of how PRD OQ-6 (required vs supplementary) resolves. Binds: Learning Experience, Certificates. Prevents: Progress bar, Continue button, and Certificate issuance each computing 'done' slightly differently (e.g. one counting optional lessons, another not).
- (decision) AD-8 Code Execution Service boundary (FR-9, FR-23, cross-cutting code-execution-security NFR): grading is invoked through one contract -- submit(exerciseId, code) -> ephemeral PGlite instance -> pass/fail plus message -- never inline in the app request path beyond that call. v1 scope is fixed to SQL only. No network egress; hard CPU/time/memory ceiling enforced by the calling process. Binds: Course Authoring (exercise-definition schema) and Learning Experience (submission/grading flow). Prevents: exercise authoring and exercise-taking evolving incompatible ideas of what a 'graded submission' contains, and blocks ad hoc eval()-style shortcuts that would violate the sandboxing NFR. Multi-language support (PRD OQ-10) extends this same contract later; does not require a new one.
- (decision) AD-9 i18n/content-language contract: UI strings live in next-intl message catalogs (en.json/ar.json) with dir=rtl driven off locale; Course content (title, description, Lesson body) is stored as single free-text fields, never per-locale columns -- Sanabel does not auto-translate content (FR-34). Binds: every UI-rendering surface (UI strings) vs Course Authoring/Discovery (content fields). Prevents: an epic building a per-locale content-translation UI that FR-34 explicitly rules out, or another epic assuming every Course has both an EN and AR version.
- (decision) AD-10 Visibility/access-gating contract: one shared canQueryCourse()/canAccessLesson() authorization function is the single source of truth for (a) Discovery's browse/search filtering out Unlisted courses (FR-14/17), (b) Course detail page rendering pre-signup (FR-18), and (c) Lesson content routes requiring Enrollment (FR-19). Binds: Discovery, Course Authoring (visibility field), Learning Experience (enrollment gate). Prevents: three independently-built surfaces (browse, detail page, lesson player) each getting the Public/Unlisted/Enrolled gate subtly wrong.
- (decision) AD-11 Moderation contract: Admin removal (FR-32) of a Course/Comment/Rating is a soft-delete (status/removedAt flag), never a hard delete. Binds: Moderation, Certificates, Course Authoring. Prevents: removing a Course cascading to hard-delete Enrollment/Progress/Certificate rows and breaking FR-15's guarantee that already-issued Certificates survive Course changes; also prevents Comment/Rating removal breaking foreign keys other modules hold.
- (decision) AD-12 Environments: single production environment on Vercel + Neon (primary branch); every PR gets a Vercel preview deploy wired to an ephemeral Neon database branch (schema+data fork of primary), torn down on merge/close. Binds: deployment/CI setup, migration workflow. Prevents: a solo builder needing to hand-provision staging infra per feature, and preview environments drifting from primary schema.
