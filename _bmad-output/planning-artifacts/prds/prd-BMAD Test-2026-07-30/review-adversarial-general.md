# Adversarial Review: PRD Sanabel (prd.md + addendum.md)

Reviewed as a cynical, skeptical reader with zero patience for hand-waving. This PRD is unusually well-organized and self-aware (it flags several of its own gaps as `[ASSUMPTION]`/`[NOTE FOR PM]`/Open Questions) — credit where due. But "launch-grade rigor" is the bar the user explicitly set, and against that bar there are real holes: some already half-admitted and left unresolved, some not admitted at all.

## Findings

- **Arbitrary code execution has zero security treatment.** FR-21/FR-9 commit to Interactive Code Exercises where learners submit code that gets executed and graded server-side (or client-side) against a sample dataset. Running untrusted user-submitted code is one of the highest-risk features a platform can ship, yet §7 Cross-Cutting NFRs — which does cover upload security, accessibility, and RTL — says nothing about sandboxing, resource/time limits, network egress restriction, or abuse prevention (crypto-mining payloads, fork bombs, infinite loops). For a solo-maintained platform expecting real public traffic, this is not a nice-to-have; it's a prerequisite the PRD is silent on.

- **"Interactive Code Exercise" is scoped as a SQL query console but glossed as general "coding education."** Every worked example (UJ-1, UJ-2, Glossary) is SQL-against-a-sample-dataset. But §2.2 Non-Users only excludes non-coding topics — nothing restricts Sanabel to SQL-only, and the platform's whole premise is general coding education. If instructors are expected to eventually author Python/JS/etc. exercises, the actual engineering scope is a multi-language sandboxed execution service, not "a console." The PRD's own "one honest flag" callout (§6.1) undersells this by describing it as "a graded, in-browser code console with pass/fail feedback" — that framing hides the harder problem: nothing defines how an Instructor authors the grading logic/expected output, what dataset formats are supported, or dataset size limits. This is authoring-tool scope with no FR coverage at all.

- **Cloudflare Stream cost-with-zero-revenue is diagnosed but never resolved, and the PRD ships without a hard control.** §8 and addendum correctly identify Stream spend as the dominant, unbounded cost with no revenue offset, and SM-C1 names it as a counter-metric to watch — but "watch" is not a mechanism. Open Question 4 ("should there be a cap?") is left open, and FR-9/FR-10 (upload authoring) specify no size/duration limit. A launch-grade PRD for a project with a real cost exposure and no revenue should not ship an unbounded upload path and defer the cap decision to "architecture" (per addendum) with no product-level requirement forcing architecture to enforce one. As written, one enthusiastic instructor uploading hours of 4K video could produce a bill Ahmed can't pay, and nothing in the FRs prevents it.

- **Bilingual/RTL scope is compressed into 2 FRs and one NFR bullet, but the real surface area is much larger.** FR-31's NFR only names three UI surfaces (course-builder outline, video player controls, progress bar). Untouched: RTL behavior of drag-and-drop reordering (FR-8), bidi handling of LTR code blocks and the code-exercise console embedded in an RTL page, RTL certificate file generation (PDF RTL text layout is notoriously fragile), transactional emails (password reset, notifications) — are they bilingual/RTL too? — and the Cloudflare Stream player's own RTL/localization support, which Sanabel doesn't control. None of this is mentioned once.

- **Content-language filtering is an unresolved contradiction, not just an open question.** FR-32 explicitly declines to require Instructors to tag content language, yet Open Question 3 asks whether such a tag/filter is needed, and Browse/Search (FR-15) has no language-filter FR at all. If an Arabic-UI learner has no way to filter for Arabic-language courses, the "bilingual platform" pitch (§4.9 description: "reflecting its name and intended audience reach") is UI-deep only — the thing that actually matters to an Arabic-speaking learner (finding Arabic content) is unaddressed and was decided as a non-requirement (FR-32) before the dependent question (OQ-3) was resolved.

- **No FR governs what happens to a Course after learners are already enrolled and it changes.** UJ-1 itself has Yousef publish a Course Unlisted with "two more modules to go" — i.e., the PRD's own primary journey assumes courses evolve post-publish with live learners on them. Yet there is no FR for: recalculating progress/certificate-eligibility when required Lessons are added after a Learner already completed the Course, notifying enrolled Learners of new content, or what happens to an already-issued Certificate when the Course it references later changes. This is exactly the kind of requirement that "sounds complete" (FR-24's consequences list what a Certificate contains) but isn't testable against the realistic case the PRD's own journey describes.

- **Same-email account merging (FR-2) is stated as a behavior without the security precondition that makes it safe.** "A social-login account and an email/password account sharing the same email are treated as the same user" is a known account-takeover vector if email/password signup isn't verified before merge (attacker pre-registers victim's email, later victim's "Sign in with Google" silently merges into attacker-controlled account). FR-1/FR-2 never require email verification before this merge logic applies — a gap that looks like a testable consequence but actually isn't safe as specified.

- **No signup abuse controls, despite manual-only moderation and free/frictionless signup.** FR-1 makes email/password signup free and scriptable; FR-30 is explicit that moderation is manual-admin-only with "no automated flagging/reporting UI." Nothing in §7 or FR-26/27 mentions CAPTCHA, rate limiting, or bot detection on signup or comment posting. Combined, a single spam run against Comments (FR-26) has no automated backstop and lands entirely on Ahmed to clean up by hand — undermining the "accepted as sufficient at low launch volume" framing in §4.8/§8, since bot-driven volume doesn't respect "low launch scale."

- **Admin-invite-only instructor flow has no discoverability path, and growth beyond personally-known instructors isn't modeled anywhere.** FR-4's note candidly admits grants happen "out-of-band" with no in-app request flow — fine as a locked decision — but no Success Metric or FR addresses how a prospective instructor who isn't already known to Ahmed would even learn that teaching on Sanabel is possible. SM-1/SM-2 validate one instructor (Ahmed himself) and one learner; there's no metric or mechanism modeling instructor-side growth at all, so the PRD can't actually tell whether this bottleneck is working or throttling adoption to zero.

- **Sequencing problem between the Safety decision and an unresolved fact.** §4.8/§8 commit to manual-only moderation as "accepted as sufficient at low launch volume," while Open Question 5 ("could minors reasonably sign up?") is left unanswered. If minors are a plausible audience — likely, for a free platform aimed at students learning to code — that materially changes the risk calculus for manual-only moderation and COPPA-adjacent obligations. The moderation posture was locked in before the fact that should inform it was resolved.

- **FR-14 ("at minimum per-Lesson completion/drop-off counts") is not actually testable as written.** "At minimum" leaves the acceptance boundary open-ended — a QA pass could accept almost any minimal dashboard and still claim compliance. For a document that otherwise prides itself on FR-level "Consequences (testable)" annotations, this is one of several FRs (FR-8, FR-15's "search" with no defined search fields) that reads as complete but doesn't actually pin down a pass/fail bar.

- **No captions/transcripts for video, despite an accessibility NFR that name-checks screen-reader usability for video content.** §7 states "Course text/video content should be usable with screen readers... where feasible," but no FR provides captions, transcripts, or any text alternative for Video Lessons — screen readers cannot meaningfully consume video without one. The NFR aspiration and the FR set contradict each other.

- **No account-deletion/data-export FR despite an explicit privacy assumption banking on "standard reasonable-care data handling."** §8 Privacy waves off formal GDPR scope but doesn't stub even a baseline "Learner can delete their account and associated data" requirement — normally table stakes for any consumer product collecting auth identity and personal progress records pre-launch, and specifically flagged as more likely to matter given the EN/AR bilingual reach the PRD itself calls out as increasing regulated-region exposure.

- **§7 has no availability/reliability/monitoring NFRs at all.** For a document explicitly targeting "launch-grade rigor" with real public traffic, there is no stated uptime expectation, no backup/disaster-recovery posture, and no mention of who gets paged or how an outage is detected for a solo-maintained platform. Video delivery performance and upload security are covered; "is the site up and who notices when it isn't" is not.

- **SM-3 is framed as a success metric but is actually a static invariant with no enforcement mechanism.** "Zero pricing/paid-access surface exists anywhere in the product at any time" is unlike SM-1/SM-2 (one-time milestone events) — it needs continuous guarantee, but nothing (CI check, design-system constraint, code review gate) is proposed to keep it true as the product evolves. As written it relies on nobody ever accidentally shipping a pricing UI, checked only by manual audit.

- **Cold-start/empty-state UX for Browse & Discovery is unaddressed.** Given instructor growth is admin-invite-only and bottlenecked (see above), Browse/Search (FR-15) will plausibly launch with zero-to-few Public Courses. Nothing in the Discovery feature or UJ-2 addresses what a Learner sees when browse/search returns little or nothing — a real experience gap for the platform's second most important journey.

## Summary

Verdict: **Not launch-ready as written.** The PRD is well-structured and unusually honest about several of its own gaps, but it ships two categories of real risk with no functional requirement covering them at all: (1) arbitrary/graded code execution with no sandboxing or abuse-prevention treatment, and (2) unbounded Cloudflare Stream cost exposure with no enforced cap, against a platform with a permanent no-revenue constraint. Bilingual/RTL and instructor-growth scope are both underestimated relative to what's specified. Several FRs marked "testable" don't actually pin down a pass/fail bar, and at least one behavior (email/social account merge) is specified in a way that looks safe but omits the precondition that would make it so.
